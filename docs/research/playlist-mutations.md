# Playlist mutation checkpoint

Snapshot: 2026-09-25.

## Current behavior

- `POST /1/playlist/create`, `POST /1/playlist/edit/{playlist_mbid}`, `POST /1/playlist/{playlist_mbid}/item/add`, `POST /1/playlist/{playlist_mbid}/item/delete`, `POST /1/playlist/{playlist_mbid}/item/move`, `POST /1/playlist/{playlist_mbid}/copy`, and `POST /1/playlist/{playlist_mbid}/delete` require authentication and use the normal ListenBrainz rate limiter.
- An empty playlist is valid. Brainz creates an empty, private playlist from the Profile Owned section; track insertion is a later workflow.
- Edit is owner-only and overwrites playlist metadata. The app therefore sends a complete title, optional annotation, privacy value, and collaborator list rather than a partial patch.
- Collaborators are selected from concrete ListenBrainz user-search results, trimmed, de-duplicated case-insensitively, and never include the owner. Add/remove work is local until Save; the existing full-snapshot edit then replaces the complete collaborator list in one non-retried POST. Failed saves preserve the draft.
- Add-item accepts owner or collaborator authority. It appends JSPF tracks by canonical MusicBrainz recording URL, permits duplicates, accepts at most 100 tracks, and has a separate optional zero-based offset route. Brainz deliberately submits one recording with no offset so the operation is append-only.
- Copy accepts any playlist visible to the authenticated caller: public playlists plus private playlists they own or collaborate on. The server creates `Copy of <title>`, assigns the caller as owner, preserves visibility, description, track order, and provenance, and removes collaborators and generated-for metadata.
- None of these endpoints exposes an idempotency key. Each tap is serialized, enters `RequestGate.shared` exactly once, and is never retried automatically. A 429 defers later work using the server delay and remains visible to the user.
- A lost transport/decoding response is not reported as a definite failure: create/edit become indeterminate, another save is disabled, relevant caches are cleared, and the UI asks the user to reconcile with the server before trying again. Cancellation while queued behind the request gate remains an ordinary no-op; cancellation after transport begins is conservatively indeterminate because the server may already have committed the POST.
- An add first reads canonical playlist detail and counts matching recording MBIDs. An existing occurrence requires an explicit **Add Another Copy** decision, whose baseline is re-read immediately before POST. After the one POST, the app fetches detail again and accepts only an increased occurrence count as confirmation. An ambiguous transport result follows the same reconciliation path without replaying the mutation; an unresolved result disables another attempt and asks the user to inspect the playlist.
- Item movement is positional and non-transactional on the current server: it commits removal before reinserting the supplied range. A lost response, malformed success, server failure, or post-admission cancellation can therefore mean that one recording moved, disappeared, or remained unchanged. The route requires a syntactically valid recording MBID in `{mbid, from, to, count}`, but selection is governed by zero-based positions. Brainz exposes only one local move per editor session and requires every slot to have canonical contiguous positions and a recording MBID.
- Reorder open, drag, reset, and cancel are entirely local. Saving uses one fresh non-coalesced full-order preflight, one serialized `count: 1` POST with no retry, then one fresh full-order postflight on the normal path. Playlist identity and the complete stable slot sequence—recording MBID, added time, and normalized contributor—must match before dispatch. Success is claimed only when postflight equals the exact requested move. Exact duplicate fingerprints are observationally equivalent; mutable title, artist, release, and artwork fields never establish identity.
- Removal and reorder share a single protected account/playlist barrier under `playlist-item-mutations-v2`. Its filename and record contain only a SHA-256 pair digest plus schema version: no token, raw username, raw playlist UUID, timestamp, title, or track metadata. A legacy `playlist-item-removals-v1` record is detected as unresolved and removed only after explicit fresh review. Missing, corrupt, unreadable, or uncleared state fails closed; another scene cannot reserve the same pair.
- Definite move rejection and 429 clear the barrier durably and perform no postflight. A 403 receives one fresh visibility check before the app either records a collaborator denial or purges inaccessible state. A 401/404 purges directly. Any other live ambiguous result receives at most one postflight; a cancelled task after dispatch leaves the barrier for explicit user review. The server has no playlist revision/conditional-move token, so another client can still race between preflight and POST; postflight prevents false success but cannot undo a wrong positional move or partial server deletion.
- Copy is transactionally non-destructive on the server but not replay-safe: every committed request creates a new playlist and no idempotency key exists. Brainz persists a token-free account/source attempt before dispatch and records the returned destination immediately. It then fetches that MBID canonically and verifies the returned UUID, normalized owner, and `copied_from` source before showing or inserting exact metadata. A lost response clears owned-list caches and leaves a durable lock across navigation and relaunch. **Check Again** performs a fresh Owned request; only a recent row whose `copied_from` matches the source can advance to canonical destination verification, and an absent match never unlocks replay.
- Whole-playlist deletion is creator-only and non-idempotent from the client’s perspective because a lost response makes replay unsafe. Immediately before deletion, Brainz performs one fresh, non-coalesced canonical detail read and requires an exact normalized creator/account match. It then durably syncs a token-free SHA-256 account/playlist barrier before admitting exactly one serialized empty-body POST. Confirmed success performs no postflight read. A verified `404` means the desired absence is already true without claiming which attempt caused it; `403` records a process-wide creator denial; `401` purges private state; transport, malformed success, server failure, or cancellation after admission remains indeterminate with no replay.
- Deletion recovery is explicit. **Check again** performs one later fresh read only after the user asks: absence confirms the desired state, continued exact ownership allows the pair-scoped barrier to be reset manually, and changed visibility/ownership purges inaccessible state. Missing, corrupt, or unreadable journal storage fails closed. The barrier remains through detail/profile cache eviction and is cleared only immediately before synchronous cross-screen removal publication, preventing a cancelled cache operation from making a second POST available.
- Saving an LB Radio result uses the populated `POST /1/playlist/create` request already in ListenBrainzKit. It always sends a normalized private title/annotation, no collaborators, and only canonical recording MBIDs in generated order; repeated occurrences are preserved because the server's JSPF creation path preserves input entries and no deduplication contract exists. No name/title matching is invented for unmapped tracks.
- Radio save is also non-idempotent. Before admission, Brainz atomically writes and syncs a protected, token-free, account-scoped barrier under Application Support. Missing, corrupt, or unreadable journal state fails closed. The barrier remains after any post-dispatch cancellation, transport failure, or malformed response. Its record intentionally contains no prompt, title, or track data, so relaunch reconciliation cannot honestly auto-match a possible playlist. The recovery path performs a fresh, non-coalesced 100-item Owned Playlists read, shows every returned row newest first, then requires an explicit user acknowledgement before clearing the barrier. Definite rejection and cancellation while still queued clear it; success clears both detail and profile-page caches and offers the returned canonical playlist detail.
- Private or unavailable playlists may produce a not-found response. Server authorization is authoritative; the owner-only Edit button is only a convenience.

## Reuse decision

- Current server/API source defines the payload and overwrite semantics.
- The current website and official Android/KMP client supplied the established search/select/remove behavior and 500–800 ms search delay evidence. Their GPL code and UI were not copied; the app reuses its native `SearchModel`, request gate, and `UserAvatar`.
- Official Android/KMP supplies mature behavior evidence: new playlists default private, collaborators are normalized/exclude the owner, and successful item additions refresh playlist state. Its GPL code was not copied.
- Current server, web, and official Android/KMP behavior supplied copy eligibility, inherited-visibility, collaborator-removal, and confirmation semantics. Their GPL code was not copied.
- Current server, website, and official Android/KMP sources supplied move eligibility, payload, positional behavior, and non-atomic failure evidence. Their GPL code and UI were not copied; the sheet uses native SwiftUI `List.onMove` and app-owned state.
- Minidisc supplies the native destination-sheet, search, and explicit duplicate-decision interaction. `PlaylistAddSheet.swift` adapts that MPL-2.0 interaction with ListenBrainz-specific paging and reconciliation; provenance is recorded in `THIRD_PARTY.md`.
- The vendored MPL-2.0 ListenBrainzKit now owns generic exact-JSPF create/edit/append requests, single-item remove/move requests, plus typed empty-body copy/delete and endpoint error mapping. These additions are upstream candidates.
- App-owned Swift code owns draft normalization, the gated no-retry mutation boundary, UI state, cache reconciliation, and the native SwiftUI form.
- Official KMP remains a behavior reference; adding it as an iOS framework would add disproportionate build/interoperability weight for these calls.

## Native slice

- Authenticated users can create an empty playlist from their Owned playlists section.
- Owners can edit a playlist name, description, and public/private status from playlist detail.
- Owners can add or remove collaborators in the same editor. Search waits 500 ms, cancels stale work (including an explicit retry superseded by a new query), caches normalized queries, coalesces exact reads through the shared gate, and accepts only a returned ListenBrainz account. Collaborators can manage tracks but cannot edit metadata, collaborators, or the playlist itself.
- Authenticated users can add an MBID-mapped recording from Recording Detail to either an owned or collaborating playlist. The searchable sheet loads and pages both categories independently; unmapped recordings never present the action.
- Authenticated users can duplicate any visible canonical playlist from Playlist Detail after a forced source refresh. Because the server has no conditional version token, confirmation says that source privacy is preserved at copy time rather than promising a cached public/private value. The returned MBID is fetched canonically; the success alert names the actual resulting visibility, offers direct navigation, and reconciles an already-loaded Owned Playlists list without synthesizing metadata from the source.
- Exact creators can permanently delete a playlist from Playlist Detail after an explicit destructive confirmation. Confirmed deletion or verified absence dismisses the detail, evicts every detail/profile cache scope, and removes the row from an already-loaded Profile list while invalidating in-flight pages so an older response cannot resurrect it. Indeterminate delivery instead leaves a visible recovery card and disables another attempt.
- Owners and collaborators can open **Reorder tracks** only when at least two fully mapped canonical slots are present and no item-mutation barrier is unresolved. Native drag handles and VoiceOver Move up/Move down actions allow exactly one move; Save and Reset then become available and further moves are disabled. Active saves cannot be cancelled or interactively dismissed. The detail updates only from the fresh canonical result, and a recovery card owns any unresolved removal or reorder barrier.
- Editing uses fresh non-coalesced mutation-inspection reads before the form opens and again immediately before POST. It cannot join an ordinary detail request that began before the edit intent. If title, annotation, privacy, or collaborators changed on the server while the form was open, the save is stopped instead of overwriting the newer snapshot. A server without conditional updates still leaves a small unavoidable race between that final GET and POST.
- A confirmed edit clears every public/authenticated playlist-detail scope and every profile playlist-page cache before restoring the authenticated confirmed value. A process-local, token-free journal also reconciles already-loaded Profile rows across tabs. This prevents a public-to-private change from leaking the formerly public detail through cache.
- The confirmed edit is then checked against one best-effort server refetch. A refetch failure retains the confirmed state and reports that fresh data could not be checked.
- Creation clears the owner-list page cache and reloads it. Duplicate submissions are blocked while a mutation is pending; failures preserve the draft and appear inline.
- Playlist detail cache keys include the normalized authenticated viewer (or public-only scope) so private data cannot cross accounts.
- Authentication or visibility loss during copy clears all playlist caches before an ordered, process-local mutation journal advances. It replaces the rendered detail with a generic unavailable state and then clears all Profile playlist state for revoked authentication or removes only the inaccessible source row. The latter invalidates in-flight responses and resets pagination until an explicit refresh, so an older response cannot restore private data or skip a shifted row. The immutable navigation seed is never used as a visible fallback after access loss.

## Deferred

Multi-item removal/reordering, import/export, and service synchronization remain separate milestones. The native item tools deliberately operate on one occurrence at a time; the server's position-based, non-atomic move still has an unavoidable race without a playlist revision or conditional mutation primitive.
